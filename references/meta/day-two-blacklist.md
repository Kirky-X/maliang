# 双域死法黑名单 —— 好界面怎么死得不知不觉

> 规范层。[`ai-tells.md`](ai-tells.md) 是视觉层黑名单(页面怎么显得廉价);本文件是**定义层**黑名单(一个好看的界面怎么死透)。输入可以是 spec / proposal / design 构思,不要求先有建成页面——这是定义级审计入口,`critique` 子命令「三问分工」之外的第四问。判定为 definition-level defect,在这里修只要改一句话;发布后发现要还债。来源:mouse-lin/finesse-brief 仓的 day-two.md,2026-10 吸收。

## 0. 使用方法与两条前置

**两域两清单**:个人域(一个人每天回访的界面)跑 D-list,系统域(围绕业务对象的多人多模块工作台)跑 S-list。混合型两边都跑,重叠很小。

**测试语**:

- 个人域:周四了,他周一开了、周二开了、周三没开。**今天的界面有什么话对他说?**
- 系统域:上线日,库里只有真实工作产生的数据。**首屏说的哪句是真的?** 第三周:**有没有任何一屏在给结论,而不是在列数据?**

**两条前置(比两份清单更早)**:

| 前置 | 内容 |
| --- | --- |
| D0 | 存在一个 V0 可检吗?个人域 ≤1 个问题、系统域 ≤2 条消息就给出一个完整方案。定义不存在时一切免谈——最常见的死法是他问了几轮、答了几轮,然后走了 |
| D0′ | spec 盖得上房子吗?首页定了 hook 底下放什么;每个频道/模块说清自己干什么;视觉基调已设定 |

# Part I · D-list(个人域 13 条)

### D1 · 幸运签 hook —— 头号杀手
- **症状**:hook 无变量(「今天也要加油哦」),或有变量没东西产出(「黄体期第 3 天」而全定义找不到锚点日期)。
- **检测**:按第 40 天空数据的场景渲染,与第 1 天相同 → 失败。或指着明天会变的分句,指不出 → 失败。
- **修法**:见 [`data-floor.md`](data-floor.md) §4 五步(推导 / 问一次 / 一键 / 或改 hook)。
- **为何活过审查**:写在提案里很美。没人会在幻灯片上否决「今天也要加油哦」,所有人会在周四忽略它。**无变量的 hook 直接禁用。**

### D2 · 百科轨
- **症状**:科普/指南/红黑榜/动作库类频道超过 1/3。
- **检测**:数。超 1/3 → 失败。
- **修法**:合并成一个科普频道,省下的席位给 Record 和 Review。
- **为何活过**:命名免费、不要求任何人做事,还让频道列表显得充实——它们是这个品类的填充物。

### D3 · 输入债
- **症状**:INPUT ≥ 留存回报;或三个频道各自索要每日输入。
- **检测**:把所有频道的每日秒数加起来,个人域超约 60s → 失败(`operation` 类除外)。
- **修法**:推导、默认、一键,或砍频道。**砍是人人跳过、却常常正确的修法。**

### D4 · 无 Review 频道
- **症状**:他每天喂,界面积累从来不回馈。
- **检测**:`ledger` / `care` 型无任何 Review 类频道 → 失败。
- **修法**:加一个(曲线 / 周报 / 相册 / 年报)。它通常也是最诚实的变现接缝。
- **为何要紧**:第三周他会发现自己一直在喂一个数据库。Review 频道是让存款变得划算的赔付。

### D5 · 假今日频道
- **症状**:叫「今日 X」的频道,内容每天一模一样。
- **检测**:写出周一和周四的内容,相同 → 是个挂着今日标签的知识频道。
- **修法**:让它对昨天作出反应,或诚实地改名。

### D6 · 空白冷启动
- **症状**:day 1 是 `--`、空图表、或六字段安装向导。
- **检测**:有没有写下来的 day-1 台词?
- **修法**:day 1 只索要**一件**输入并说清它换来什么;永不演示数据——事后被发现编造的数字会毒化页上其余一切。
- **为何致命**:他活不到第二天,其余十二条永远没机会起作用。

### D7 · 十频道列表
- **症状**:频道数 > 9。
- **检测**:数。> 9 失败;8–9 逐个给理由。
- **修法**:按「同一时刻、同一原因打开的频道是一个频道」合并。

### D8 · 贴上去的接缝
- **症状**:商城 tab 不挂任何频道;或在他正难受时打开的那个频道里推商品。
- **检测**:说出接缝从哪个频道长出来。说不出 → 失败。那个频道是痛/焦虑频道 → 失败。
- **修法**:把接缝挪到 Review 或 Knowledge 频道,或诚实地写 `seam: none yet`。
- **变现伦理(并入 D8)**:seam 必须能说出它来源的频道,否则写 `none yet`;痛苦/恐惧频道禁商业;`banned_channels` 明写进 spec——因为开发和下一次 monetize 时,转化率最高的位置会重新显得诱人,而拒绝它的理由不写下来就没人看得见。

### D9 · 想象中的时刻
- **症状**:定义里的时刻不在他真实的一天里(「每天早上冥想 20 分钟」而用户 8:40 起、9:00 上班)。
- **检测**:请他描述昨天,那个时刻在里面吗?
- **修法**:挂到已有的时刻上(通勤 / 睡前刷手机 / 练完那一下 / 收摊后)。**永远不要为了使用本应帮他的工具,而请他先养成一个新习惯。**

### D10 · 范围膨胀
- **症状**:一个人的生活工作台长出了「XX 管理系统」、角色、设置中心、登录页、「以后还能给别人用」。
- **检测**:标题命名的是人还是物件?并且域判定仍回个人(无「一共有 N 个 X」、无页面树)?
- **修法**:改以人/物件命名;删掉一切只有第二个**账号**才有意义的功能。
- **两个必须分清的东西**:①双读者(妈妈+孩子)不是范围膨胀——一个 owner、一个域、一句 hook;②真正的系统工作台是另一个域,不是膨胀(「十个销售要一个跟客户的台子」合法地有角色)。先用域判定:**是系统域就直接换 S-list**,不要再套 D10。

### D11 · 断签惩罚者
- **症状**:「已断签 3 天」、熄灭的火焰、带窟窿的曲线、补录才能记今天。
- **检测**:有没有为回归用户写好的重新入口台词?
- **修法**:见 [`data-floor.md`](data-floor.md) §6。让回来这件事零成本。

### D12 · 编造实质
- **症状**:科普/报告/情报频道的内容由模型现场编——听着像真的医学、金融、法律判断,无来源。
- **检测**:逐个内容频道说出内容从哪来。「模型写」→ 失败。
- **修法**:指名真实来源,或把频道收窄到能诚实产出的东西(他自己的记录 / 公开数据集 / 精选链接清单)。**含自信编造内容的科普频道比没有它还糟**——这个错误真的能伤人。

### D13 · 变成监控工具(本清单最糟的一条)
- **适用**:任何主体有自己意志的 `care` 类(学龄孩子 / 青春期 / 爸妈)。
- **症状**:hook 汇报**亏欠**(今天又没背完 / 这周有 3 天没读 / 落后同龄人);记录是关于他写的、不对他可见;有人是为了记录而观察。
- **检测**:在心里把 hook 念给主体听。念出来难堪 → 已经发生了。第二查:有没有人为了填某个字段而必须**观察**他?「以观察为输入」是监控的客气说法。
- **修法**:陈述进度而非亏欠(「这周读了 4 天」同样数据,念得出口);记录默认对主体可见;从过程记录降到**周级结果记录**(通常是正确答案,就是刻意做一个周频工作台)。
- **为何最糟**:其余十二条死于没人打开;这条死于一段受损的关系。它还最可能早期看起来像成功——第一周依从性很高,依从不等于有效。

# Part II · S-list(系统域 11 条)

### S1 · 演示数据谎 —— 头号杀手(个人域 D1 的对应)
- **症状**:结论条写着「12 个待跟进 · 3 个超期」,spec 里没有任何东西产出那个 12 或 3。
- **检测**:对空库渲染首屏。冷启动台词之外出现任何数字 → 数字来自想象。然后把每个数字回溯到带写入方的字段。
- **修法**:回溯不到的数字从 hook 里拿掉。
- **为何活过审查**:和幸运签不同,它**看起来严谨**——真实感的数字、像样标签。它一路读到上线日,那是最贵的露馅时刻。

### S2 · 列表页地狱
- **症状**:每个模块的 L1 都是「表格 + 搜索框 + 分页」,九个模块九张同样的屏,没有一屏给结论。
- **检测**:读每个模块 L1 的 shows,三个及以上说「表格」→ 失败。
- **修法**:`primary` 模块的 L1 是看板 / 分诊列表 / 曲线 / 卡片阵;表格归 `registry` 模块和次级查询,默认排序按**什么需要关注**而不是创建时间倒序。
- **为何要紧**:工作台和数据库查看器的唯一区别是有一处东西说该做什么。一面表格墙永远不说。

### S3 · 空后台
- **症状**:`cold_start.day_1` 描述空页长什么样,而不是命名一个动作。
- **检测**:day 1 里有没有用户会执行的动词?
- **修法**:命名一个带可见入口的具体动作(拖一份 Excel / 建第一个 Agent / 录一个客户,只要名字和电话)。**registry 和 console 类空时不是稀疏,是无用。**

### S4 · 名词模块
- **症状**:客户管理 / 订单管理 / 数据管理 / 系统管理。
- **检测**:任何以「管理」结尾的模块名;或 `does` 里没有动词。
- **修法**:命名对象,动词放进 `does`。
- **为何活过**:听着像正经模块组合,是企业版的「今天也要加油哦」。

### S5 · 权限幻觉
- **症状**:spec 里三个角色,每个角色看到同样的屏。
- **检测**:找一个两个角色 shows/actions 不同的模块。找不到 → 失败。
- **修法**:合成一个角色,或说出真实差别(通常是「只看自己的」)。**一个守不住任何东西的登录,花掉一个构建周,买到零。**

### S6 · 未建成的集成
- **症状**:hook 依赖「ERP」「支付系统」「设备上报」的数据,无 API、无负责人、无日期。
- **检测**:每个 `written_by: integration` 字段问:那个系统今天在跑且可达吗?
- **修法**:`exists_today: false` 进 depends_on 并写明 until_then,数字离场。
- **为何贵**:定义时不可见,构建时不可修。构建者造不出这个集成,只能带着个 0 上线——而本该是数字的 0 比诚实空态更糟。

### S7 · 孤儿模块
- **症状**:和 subject 无关的模块(CRM 里的公司公告、工厂看板里的员工考勤)。
- **修法**:砍掉,或承认它是第二个工作台并记 deferred。

### S8 · 对称页树
- **症状**:每个模块都恰好 L1/L2/L3。
- **修法**:设置只到 L1;没有真正子记录的模块停在 L2。**深度跟数据走,不跟版式走。**

### S9 · 角色 = 组织架构图
- **症状**:定义期五个以上角色。
- **修法**:只标一个 `opens_daily: true` 并为他建;其余每个一行。他在描述一家公司,不是一个工作台。

### S10 · 无 Review 模块
- **症状**:每个模块要么列东西要么收输入;没有模块把积累变成结论。
- **检测**:零 Review 类模块 → 失败。
- **修法**:加一个(月度复盘 / 周报 / 成功率与耗时 / 生产报表)。系统域最容易跳过的就是它——「报表有 BI 做」。没有它,这是个带漂亮页头的数据录入面。

### S11 · 人人都是 primary
- **症状**:没有 weight,或所有模块平权。
- **修法**:只留一个 `primary`——opens_daily 角色落地那个。均侧栏是「从没决定过什么重要」的视觉形态。

## 24 项扫描清单(过 remain 全项)

**先跑两条前置(两个域都跑)**:

```
[ ] D0  存在可检的 V0(个人域 ≤1 问;系统域 ≤2 条消息)——其余项都以它为前提
[ ] D0' spec 盖得上房子(首页内容定 / 每模块有活干 / 视觉基调已设)
```

**D-list(个人域)**:

```
[ ] D1  hook 有变量,且有字段产出它
[ ] D2  Knowledge 频道 ≤ 1/3
[ ] D3  每日输入 < 回报,且 < 约 60s
[ ] D4  至少一个 Review 频道
[ ] D5  今日频道周一到周四不一样
[ ] D6  day-1 台词已写,只索要一件事,无假数据
[ ] D7  频道数 4–9
[ ] D8  接缝挂在具名、不痛/焦虑的频道上(或 none yet)
[ ] D9  时刻存在于他真实的一天
[ ] D10 标题以人/物件命名(先过域判定:真系统域是另一个域,不是膨胀)
[ ] D11 间断后回归零成本
[ ] D12 每个 Knowledge/feed 频道有真实来源
[ ] D13 (有意志主体的 care)hook 陈述进度、记录主体可见、无人以观察为录入
```

**S-list(系统域)**:

```
[ ] S1  结论条每个数字回溯到带写入方的字段
[ ] S2  primary 模块的 L1 不是表格
[ ] S3  day 1 命名具体第一个动作(有导入路径更好)
[ ] S4  无「XX 管理」命名;每个 does 有动词
[ ] S5  任意两个角色有真实差异,否则是一个角色
[ ] S6  每个 integration 字段今天存在,或进 depends_on 并离场
[ ] S7  每个模块与 subject 有关
[ ] S8  页深跟数据走(设置只到 L1)
[ ] S9  角色 ≤4,只有一个 opens_daily
[ ] S10 至少一个 Review 模块
[ ] S11 只有一个 primary 模块
```

## 汇报规则(audit 口径)

汇报**只用用户语言,永不出现 D-编号/S-编号**,按**距死亡的时间**排序,不按抽象严重度:

- 按 time-to-death 分档说:S1/S6 与 D1/D6 上线日即死;S2/S10 是第三周的事;D8/S7 是慢性泄漏。用户修 bug 的注意力有限,让他按顺序花。
- 每条给:哪一句会死(举例当前文案)、为什么死、最省事的修法(一个动作)。
